# Database migrations (Alembic)

Until Phase 0, the schema was managed by `Base.metadata.create_all()` plus
`database.sync_missing_columns()`. That combination can only **add nullable
columns** — it cannot rename, drop, retype, add a constraint or index, or
backfill data. Alembic now owns schema evolution.

The database URL comes from `app/config.py` (i.e. your `.env`), not from
`alembic.ini`. There is no connection string in any committed file.

Run every command below from the backend directory (the one containing
`alembic.ini`).

---

## One-time adoption on an EXISTING database

Your current database already has every table. Do **not** run `upgrade` —
tell Alembic the schema is already at the baseline:

```bash
alembic stamp 0001_baseline
```

Then apply everything after the baseline normally:

```bash
alembic upgrade head
```

Verify:

```bash
alembic current
```

## A brand-new database

```bash
alembic upgrade head
```

---

## Adding a migration

1. Edit the models in `app/models.py`.
2. Autogenerate a revision:

   ```bash
   alembic revision --autogenerate -m "short description"
   ```

3. **Read the generated file before running it.** Autogenerate is a
   starting point, not an authority — it does not detect renames (it sees a
   drop plus an add, which loses data), and it needs help with server
   defaults and data backfills.
4. Apply it:

   ```bash
   alembic upgrade head
   ```

To preview the SQL without executing it:

```bash
alembic upgrade head --sql
```

---

## Retiring the legacy bootstrap

`app/main.py` still runs `create_all()` + `sync_missing_columns()` at
startup, guarded by the `AUTO_CREATE_SCHEMA` setting (default `true`, so
behaviour is unchanged from before Alembic existed).

Once every environment — local, staging, production — has been stamped and
upgraded, set:

```
AUTO_CREATE_SCHEMA=false
```

and let Alembic be the only thing that touches the schema. Keep it enabled
for at least one release so a missed environment fails safe rather than
starting against an incomplete schema.

## Revision notes

| Revision | Purpose |
|---|---|
| `0001_baseline` | Adoption baseline. Idempotent `create_all(checkfirst=True)`. Downgrade deliberately raises — it would drop the whole patient database. |
| `0002_pending_booking_structured_fields` | Adds `patient_id`, `doctor_id`, `start_at`, `reason` to `pending_bookings` so verifying a pending booking creates a real, schedulable appointment instead of a label-only shell. |

`0002` checks for each column before adding it. That is a consequence of
the baseline being built from current model metadata (a fresh database
gets these columns from `0001`). Revisions written from here on can be
ordinary strict autogenerated ones.
